# ADR-001: Execution Posture and Set Closure

> Status: accepted
> Date: 2026-10-08

## Context

Seven questions had to be settled before the module-extensibility effort (and the nested-repo work that precedes it) could start, because each one blocked a different half of "how does work actually land". Two process directives pulled in opposite directions: the standing dev-ai mandate to split independent work across parallel agents, versus an inherently serial gate chain (16 dependency edges, 4 parallel sets) plus a per-PR CI that runs only the Feature suite while the full suite runs nightly. That tension forced the execution-posture question — full parallel landing would accumulate unverified cross-suite breakage between nightly runs, full serial would violate the mandate for provably file-disjoint work.

Parallel waves then exposed three concrete bottlenecks around how changes reach origin and nightly CI. Nested `misc/BAGArt/*` repos are pushed only by the user (K26), with a single batch-scoped agent override that expired with the Q15-A batch (K27); CI installs prod packages from origins, so an unpushed nested commit is invisible to it (K16); and the daily nightly is pinned to `composer.prod.lock`, so even a pushed change reaches nightly only after a lock refresh (K18). Those facts made nested pushes and the one shared lock file serialization points that no existing decision owned, while the earlier nested-repo sync decision had already fixed the executor (user) for git writes.

Two further questions fixed when work may start and in what order it ships: the task-file precondition written unscoped in Q1 read as a global gate, but three research sources scoped it differently; and the D1–D4 directions themselves needed scope and phase order before any task file could exist. Together the seven decisions define the effort's execution posture: what runs in parallel, what serializes, who pushes and who refreshes, what must be true before an item starts, and in which order the directions ship. This ADR is the durable record after the per-question files are deleted.

## Decision

### Parallel within sets, serialize the merge (source question: `execution-model-parallel-vs-serial`, resolved 2026-10-07)

**Option 3 — parallel within sets, serialize the merge** (decided 2026-10-07), adopted as the default execution posture for the whole effort: agents work concurrently inside each gate-matrix set, but a set lands as one merged PR at a time — queue merges, run the narrowest suite per step (the Feature suite per PR) and the full suite at set boundaries — with the dependency-edge list remaining the only serialization authority. Fallback to option 1 (free parallel landing) for clearly isolated single-file items where nothing is serialized against (B1 option M data-only fix, pure doc fixes). Binding set-closure checklist (already consumed by Q13 and Q10): **set closes = nested batch pushed (user-executed, Q10) + prod lock refreshed iff package-affecting (Q13) + Feature suite green; nightly confirms at next pinned run.** Rejected: option 2 (serial execution in wave order) because it contradicts the standing dev-ai parallel mandate and serializes proven file-disjoint work; option 1 as the default because per-PR CI runs only the Feature suite, so cross-suite breakage from parallel merges would accumulate nightly. Binding obligation: the posture must be restated verbatim in the first task file so implementation sessions do not re-litigate it.

### Scheduled nested-push checkpoints at set boundaries (source question: `nested-push-execution-under-parallel-waves`, resolved 2026-10-07)

**Option 3 — status quo + scheduled push checkpoints** (decided 2026-10-07). K26 and K27 stay exactly as resolved: nested git writes are agent-prepares / user-executes, and no batch-scoped agent-push override is renewed. What is added is cadence: at each set-boundary merge point the agent emits the per-repo push inventory (K26's existing mechanism), the user runs one batch push, and **the set does not close until the batch is pushed** — plus the prod-lock refresh when the set touched a `composer.prod.json` package (Q13), giving the full closure rule "set closes = nested batch pushed + lock refreshed (iff package-affecting) + Feature suite green". Executor: the user executes every nested push; the agent only prepares the inventory. Binding obligation: each workstream's task file must state its push dependency in `Requirements:` (Q6's scoped precondition). Rejected: option 1 (unstructured status-quo cadence) because it contradicts Q13's already-resolved set-closure checklist and leaves CI visibility unpredictable; option 2 (standing agent-push override for this effort) because re-opening K27 is an owner decision this file cannot make and it would authorize pushes into 21 nested repos where 0 have working git hooks — it remains valid only as an explicit future re-opening of K27 with hook installation as a precondition.

### Conditional prod-lock refresh at set closure (source question: `prod-lock-refresh-serialization-point`, resolved 2026-10-07)

**Option 2 with a corrected trigger** (decided 2026-10-07). The prod-lock refresh is conditional on package-affecting merges, never a per-set or end-of-effort ritual: when a set closes, if the set changed any `misc/BAGArt/*` package that appears in `composer.prod.json` (any pushed commit, not only `composer.json` edits — the lock pins commit refs) or either host manifest, the closure checklist runs `cmd/deps/update --mode=both` + `cmd/deps/check` before the next set starts; pure host-app/docs sets skip it. Executor: the user, through the standing `cmd/deps/*` flow (K27 — nested git writes stay with the user; the agent only prepares the package-touch diff), paired with the nested-push checkpoint. Rejected: option 1 (refresh at every set boundary) because it is the same rule with a vaguer trigger and an unconditional per-set gate, rejected in favor of the checkable "did this wave touch a prod-dependency package?" test; option 3 (refresh only at effort end / let nightly catch it) because it defeats K18's pinned-lock purpose and reintroduces the 2026-10-02 stale-lock failure class. Residual risk and follow-up: `cmd/deps/check` has no tip-freshness control, so the checklist entry is the only guard until one is added.

### Nested repo sync: minimal unblock now, inventory batch review afterwards (source question: `nested-repos-git-sync`, resolved 2026-10-01)

**"C now, then A"** — user decision 2026-10-01: push only the already-committed rename-blocker commits of the 3 blocking repos (the agent writes no new nested content), refresh the lock, land the nightly rewrite; afterwards the agent prepares a per-repo inventory for the user's batch review as the step-5 prerequisite. The standing rule stays intact: no git write operations in nested repos — the user reviews and commits, the agent only edits files on disk. Execution recorded 2026-10-01: pushes done (antispam, module, access), `composer.prod.lock` refreshed, `lock-fresh:prod` green. Rejected: option B (one-time exception — agent commits and pushes all nested repos + host) because it overrides the standing rule, writes a large history as the agent, and pushed state is hard to undo; option C alone (minimal unblock, full sync later) because nightly test jobs would stay red and the false-red problem would persist — hence C only as the immediate unblock with A afterwards.

### Q15-A batch-scoped agent git-write override (source question: `q15a-agent-execution-scope`, resolved 2026-10-01)

**Option A — full agent execution** (user decision, 2026-10-01). Batch-scoped override of the workflow-git standing rule: the agent MAY git-write in `misc/BAGArt/*` for the Q15-A batch only (user approval 2026-10-01). Standing rule unchanged afterwards: nested commits stay with the user — the override expired with the batch (K27). Rejected: option B (host-side only) and option C (prep only) because both leave nested commits/pushes with the user when the batch inventory already enumerates every proposed commit — reviewing that inventory is the review the rule intends, so full execution was the fastest safe path for this batch alone.

### Scoped task-file precondition for wave start (source question: `bug-wave-start-precondition`, resolved 2026-10-07)

**Option 2 — scoped precondition** (decided 2026-10-07). The precondition binds per scope, and no rule is weakened (a task file remains mandatory for every code change):

- **D-workstreams (W-D1..W-D4):** precondition satisfied by Q1's resolution.
- **Each bug/workstream item** needs (a) its own `docs/tasks/<topic>.md` with `Requirements:` researched from the reports, and (b) only its own gating question answered: `B2`/`B3a` → Q4 (owner capability call, still OPEN at decision time), `B4b` → Q5 (RESOLVED 2026-10-07), `W-Q2` → Q2 (RESOLVED), `W-Q3` → Q3 (RESOLVED), `B1`/`B3b`/`B4a`/`B5` → no gating question.

Unblocked at decision time: `B1` (option M), `B3b`, `B4a`, `B5`, `B4b`; still gated: `B2`, `B3a` on Q4. Rejected: option 1 (global precondition with one umbrella task file) because the umbrella file conflicts with the per-topic task-file convention and its global wording was superseded by Q1's own decision text; option 3 (wait for all five answers Q1–Q5) because it would bind independent, file-disjoint bug fixes to Q4 with no dependency edge supporting that.

### Phased cheap-first scope and order for D1–D4 (source question: `module-extensibility-scope-order`, resolved 2026-10-07)

**Option 1 — phased cheap-first.** Scope = all four directions (D1, D2, D3, D4-narrowed) plus the G8/G10 doc fixes, because the opening user request named clean plug-in, menu, management, and audit. Order: phase 1 = D1 + doc fixes (executable as parallel agents; D1's scope fixed at validate+document); phase 2 = D3 (smallest structural blast, closes the named audit gap, zero schema change); phase 3 = D2 as a dedicated session, gated on Q4 (gate edge 3) whose repair-vs-retire answer adjusts D2's content but not this order; D4 stays a separate narrowed track (web activation surface + the two sanctioned cleanups and the dead-path retirements only, inside the resolved dual-support decision). Task-file precondition in its final scoped wording: the D-workstreams needed Q1's answer first; each bug/workstream item needed only its own gating question (Q6's scoped decision) — a task file remains mandatory for every code change. Per-direction `docs/tasks/` files may be created once Q1's resolution exists; bug-wave start remains governed by Q6, and within-phase parallelism by the gate-matrix sets + Q9. Rejected: option 5 (D1 + doc fixes only) because it under-delivers the explicitly requested menu, audit, and management work; option 2 (D2 first) because its premise broke twice (field-level unification buys little; the second channel is production-broken and forked into Q4) and gate edge 3 blocks W-D2 until Q4 answers; option 4 (all four in parallel) because of D1↔D2 merge friction on shared descriptors/host config plus edge 3, with the parallel-vs-serial posture deliberately deferred to Q9; option 3 (D3 first) because it merely reorders D1 and D3, which are file-disjoint in Set 1 — it costs no parallelism while D1-first matches the request's primary goal and is the cheapest item.

## Consequences

- **Contracts touched:** the standing nested-repo git rule (agent-prepares / user-executes, with the Q15-A batch as the only — expired — override); the task-file precondition ("never write code without a task file", now scoped); the dev-ai parallel multi-agent mandate; the standing `cmd/deps/*` composer flow; the nightly's pinned `composer.prod.lock` (K18) and its origins-only package resolution (K16).
- **What depends on these decisions:** every workstream and bug item's `Requirements:` (each must state its push dependency), the gate-matrix edge list as the sole serialization authority, Q1's phase order and set membership, the set-closure formula consumed by nightly verification, and the nightly full-suite/coverage runs as the confirming gate at each set boundary. B2/B3a stay gated on Q4; D2's content awaits Q4's repair-vs-retire answer.
- **Follow-ups:** restate the execution posture verbatim in the first task file; add a tip-freshness control to `cmd/deps/check` (today the checklist entry is the only guard against a lock lagging a pushed tip); any standing agent-push of nested repos requires an explicit re-opening of K27 with git-hook installation as a precondition (0 of 21 nested repos currently enforce commit-prefix/LF); keep each task file's `Requirements:` aligned with the scoped precondition rather than any earlier global reading.
