# ADR-002: Prod Lock, Nightly CI, and Repo State

> Status: accepted
> Date: 2026-10-08

## Context

These ten decisions were forced by one structural fact: the host repo's `misc/BAGArt/` tree is gitignored, so a fresh CI checkout contains no package sources, while production servers install packages through `composer.prod.json` + the committed `composer.prod.lock`. The nightly workflow had never been green (25/25 red since 2026-09-06), the prod lock had drifted (`lock-fresh:prod` red, stale because a private repo blocked refresh), and the "prod install" semantics turned out to differ from their documentation: `prefer-stable` made stable tags beat `dev-main`, so tagged bagart packages silently pinned to 2026-08-25 code.

The decisions therefore cluster around four forcing problems. First, **prod lock vs tip-of-tree**: what the nightly gate actually installs (byte-for-byte server parity, or fresh package tips), and how to keep the lock fresh without turning releases into the freshness cadence. Second, **nightly CI reliability**: how package sources reach CI (cloning into `misc/` vs vendor-mode installs like a server), how testsuites execute when everything lives under `vendor/`, and how dev tooling (pest, baseline) exists at all under a prod install. Third, **manifest and repo state**: which manifest is the full manifest, which repos are visible to CI, which branch is the default, and which packages exist publicly at all. Fourth, **hygiene items surfaced along the way**: composer SBOM scope and the versioning/availability of edge-case packages. Each question was answered by a recorded user decision with rejected alternatives and binding follow-ups; this ADR consolidates them as the durable record after the per-question files are deleted.

## Decision

### Nightly pinning: pinned `composer.prod.lock` for the daily nightly (source question: `nightly-prod-lock-vs-tip`, resolved 2026-10-01)

**Option A** — the daily nightly runs `cmd/deps/install --mode=prod` against the committed, pinned `composer.prod.lock` (prod parity). Decided by the user 2026-10-01. Rejected: **B** (tip-of-tree `composer update` per run) because red could arrive from any of 17 repos' default branches with no host action possible, plus slower installs and lock churn; **C** (hybrid daily-lock + weekly-tip) because two install paths were not needed yet. Binding obligations: prerequisite is a lock refresh (`cmd/deps/update --mode=prod`); **revisit option C (weekly tip run) after the Q7 step-5 checkpoint (3 green runs) is stable** — tip-of-tree belongs to package repos, not to the host gate.

### `composer.prod.lock` tag hijack fixed by deleting stale tags (source question: `prod-lock-tag-hijack`, resolved 2026-10-02)

**Option A** — delete the stale tags that hijacked `@dev` resolution (`bagart/telegram-bot-lib` v0.1.0/v0.1.1, `bagart/php-async-kernel-client` v0.1.0/v0.1.1, `bagart/telegram-platform-devops-baseline` v0.1.0; remotes + local), then `cmd/deps/update --mode=prod` so all bagart packages lock to default-branch tips as documented. Decided by the user 2026-10-02; executed the same day and re-verified 2026-10-07 (no tags on local or remote of all three repos, all 20 `bagart/*` lock entries at `dev-main`, `telegram-bot-lib` lock ref equal to `origin/main`). Rejected: **B** (cut fresh releases via `cmd/release/lib`) because lock-refresh cadence would become release cadence with three gated public publishes, and `bagart/ask-client`'s tip is a breaking `refactor!` whose next version must be an intentional release, not a freshness fix; **C** (explicit `dev-main` constraints for the three packages) as an asymmetric per-package special case that the user did not need once tags were deleted, now moot. Binding obligations: `prefer-stable` in `composer.prod.json` and the tag flow in `cmd/release/lib` remain live, so **refresh `composer.prod.lock` immediately after any future `cmd/release/lib` tag** — ideally backed by a tip-freshness control in `cmd/deps/check`, which does not exist today (`lock-fresh:prod` validates only lock↔manifest consistency, not tip freshness).

### Nightly CI gets package sources via vendor-mode composer install, not cloning into `misc/` (source question: `nightly-ci-nested-repos`, resolved 2026-10-01)

Decided option (user, 2026-10-01): **"misc is a dev-only environment; everything installs via composer into the vendor directory."** CI gets package sources exactly like a server — `COMPOSER=composer.prod.json` VCS installs into `vendor/bagart/*` (the overlay already exists and is path-repo-free); the workflow's stub block becomes unnecessary. Rejected: **A** (clone the 17 public nested repos into `misc/` in CI) because `misc/` is dev-only and the vendor strategy supersedes it; **B** (keep stubs and accept a permanently red nightly) because Q7/Q8 enforced floors would stay unreachable and the nightly would remain decorative red; **C** (slim the nightly to jobs that can pass) because it deletes the QA layer instead of fixing it. Binding obligations: execution details are decided in the follow-up decisions below (vendor test execution, private proxy access, prod-lock pinning).

### Nightly test jobs rewrite path roots `misc/BAGArt/` → `vendor/bagart/` (source question: `nightly-vendor-test-execution`, resolved 2026-10-01)

**Option A** — after `cmd/deps/install --mode=prod`, an ephemeral-checkout script rewrites `phpunit.xml` testsuite dirs and `composer.json` autoload-dev roots from `misc/BAGArt/` to `vendor/bagart/` (case differs), then `composer dump-autoload`. Dev machines are untouched (no double-run via the dev-mode symlinks), full-suite/coverage/mutation stay in the host nightly, the stub block is deleted. Executor: user, 2026-10-01. Rejected: **B** (split suites to each package repo's CI) because the host `composer test` chain still references package testsuites, the Q7 mutation floor would lose its home, and 17 new workflows would need maintenance; **C** (publish to Packagist for fallback) because the publishing decision is far larger than the nightly fix and `@dev` refs still need VCS anyway. Binding obligations: prerequisite — refresh `composer.prod.lock` first.

### `bagart/tgbot-module-proxy` made public for CI access (source question: `nightly-private-proxy-access`, resolved 2026-10-01)

**Option A** — make `bagart/tgbot-module-proxy` public like the other 17 nested repos (zero secrets; `GITHUB_TOKEN` suffices for composer VCS auth; unblocks `lock-fresh:prod` refresh on any machine). Decided by the user 2026-10-01. Rejected: **B** (keep private, add a read-only Actions token via `COMPOSER_AUTH`) because it means minting/rotating/scoping a secret, leaves `lock-fresh:prod` machine-dependent, and every fresh clone or agent environment would need the same credential; **C** (exclude proxy from the nightly install) because it diverges from the real prod manifest and opens a QA hole exactly where the biggest module lives. Binding obligation: **precondition — run a secret audit of the proxy repo history before flipping visibility.**

### Prod manifest becomes the full manifest (source question: `prod-manifest-dev-tooling`, resolved 2026-10-01)

**Option A** — `composer.prod.json` mirrors dev's `require-dev` and `autoload-dev`, gains the `bagart/telegram-platform-devops-baseline` VCS repository, and its lock is regenerated **with** dev packages (still pinned, still no path repos); `cmd/deps/install --mode=prod` passes `--no-dev` so servers keep exactly their current installed set; nightly installs with dev via `--mode=prod --dev` and then rewrites misc→vendor paths. Decided by the user 2026-10-01. Rejected: **B** (a third `composer.ci.json`/`composer.ci.lock` manifest) because it adds a third lock to keep fresh and a third parity target — manifest sprawl for what is a mode flag in A; **C** (two-phase CI install: pinned prod runtime then unpinned dev tooling) because tooling versions would be unpinned, violating the pinned premise for exactly the jobs that run them, plus two resolutions per job. Binding obligations: the dependency-structure change is approved only in this shape (two manifests, two locks, parity rule extended to `require-dev`); the `--no-dev` server-path change is part of the decision.

### Composer SBOM deferred (source question: `composer-sbom`, resolved 2026-09-29)

**Option B** — defer the composer-specific SBOM with zero code and zero dependency changes. Rationale: the hard SBOM requirement was historical (lived in deleted `docs/tasks/devops-safe/` docs, removed in `db3c45b`), no committed check references SBOM, and composer packages are already covered de facto by the `anchore/sbom-action` workspace scan (syft's composer-lock cataloger over `composer.lock`/`composer.prod.lock`) plus the buildkit image attestation and cosign signing. Rejected: **A** (add the `cyclonedx/cyclonedx-php-composer` plugin) because it adds a dependency and an `allow-plugins` entry for no uncovered requirement; **C** (hand-rolled SBOM in the release script) because it is bespoke code to maintain and there is no release workflow for it to attach to. Binding obligations: the doc edit rewording `docs/STATUS.md` § "composer-SBOM deferred — image SBOM (workspace scan + buildkit attestation) covers release artifact" (which also fixed the dead "25 test failures" claim); **revisit only on a formal attestation request.**

### Example module published as a composer package (source question: `example-module-ci-availability`, resolved 2026-10-03)

**Option A** — publish `bagart/tgbot-module-example` as a real composer package (add `composer.json`, push the existing GitHub repo, require it in `composer.prod.json`, add a path repo entry to the root `composer.json`, add the rewrite-map entry, regenerate `composer.prod.lock`) so nightly keeps the full ~36-test module-engine E2E signal, while `TG_MODULE_ENABLED_example=false` stays in force for non-test boots. Decided by the user 2026-10-03; execution started the same day. Rejected: **B** (keep the example local-only and skip-guard the dependent tests) because nightly would silently lose ~36 of its deepest module-engine E2E assertions (skips read as green) and doctor version coverage; **C** (CI-only checkout of the example into `misc/`) as a hack that contradicts the "prod mode = no misc/" principle. Implementation deviation recorded 2026-10-03 (binding): the per-test `config()` force-enable does not work because the registry is built once at boot — instead a single central forced env lives in the host `phpunit.xml`, `<env name="TG_MODULE_ENABLED_example" value="true" force="true" verbatim="true"/>`; `verbatim="true"` is required so Laravel's `env()` receives the literal `"true"` and the typed `TgModuleConfig(enabled: bool)` does not fatal. No per-test `config()` overrides were added. The package ships with default branch `main` and no tags — no tag-hijack risk.

### Antispam unified onto branch `main` (source question: `antispam-default-branch`, resolved 2026-10-02)

**Option A** — fast-forward push `master` → `main` (`git push origin master:main`), then switch the local checkout to track `main` so `master` cannot drift again, and refresh `composer.prod.lock` to pick up `dev-main @ 475a8a9`. Decided by the user 2026-10-02; executed the same day, execution re-verified 2026-10-07. Rejected: **B** (switch the GitHub default branch to `master`) because antispam would remain the only repo whose default is `master`, institutionalizing an outlier every future `main`-based convention must special-case; **C** (leave as is) because nightly and servers would keep installing 2026-09-17 antispam while the Q15-A batch never reaches CI. Binding obligations: work on antispam happens on `main` (default = working branch, uniform with the other repos); deleting the leftover duplicate `origin/master` ref is optional cleanup, not a blocker.

### `ask-queue` stripped in CI, then published (source question: `ask-queue-versioning`, resolved 2026-10-01, executed 2026-10-02)

**Option B** (2026-10-01, user: "+") — the CI rewrite strips the `AskQueueLib` testsuite and the `BAGArt\AskQueue\Tests\` autoload-dev entry in the ephemeral checkout with a loud log line; local dev unchanged. **Option A** (publish `bagart/ask-queue` via `git init` + public repo + require wiring + committing async-kernel's dirty dependency) becomes a first-class item of the Q15-A batch review. Rejected: **C** (do nothing and let the rewrite fail on the missing directory) because nightly install/infra jobs would break on the testsuite step, contradicting the approved plan. Execution recorded 2026-10-02: repo `github.com/bagart/ask-queue` created (`e632b26`, public); dev wiring = path repository `misc/BAGArt/ask-queue` plus the existing PSR-4 `BAGArt\AskQueue\` root autoload (a dev `require` entry is forbidden by the `deps-mode-purity` control); prod wiring = VCS repository + `require "bagart/ask-queue": "@dev"`; both locks regenerated via `cmd/deps/update --mode=both` with `cmd/deps/check` EXIT 0; the rewrite script switched from strip to plain map (`ask-queue => bagart/ask-queue`), so the AskQueueLib suite now runs in CI from `vendor/bagart/ask-queue/tests`.

## Consequences

- **Contracts and files touched:** `composer.prod.json` / `composer.prod.lock` (full manifest with `require-dev` + `autoload-dev` + baseline + example + ask-queue VCS entries; all bagart entries at `dev-main`), root `composer.json` (path repo entries), `cmd/deps/install` prod branch (`--no-dev`; nightly uses `--mode=prod --dev`), `cmd/deps/update --mode=prod|both`, `cmd/ci/rewrite-vendor-paths.php` (misc→vendor map including `ask-queue`, no `example` residual allowlist needed), host `phpunit.xml` (testsuites + forced `TG_MODULE_ENABLED_example=true`), nightly workflow install/test steps (stub block deleted).
- **What depends on these decisions:** the nightly `full-suite` gate and the Q7 step-5 "3 green runs" checkpoint (drop `continue-on-error`) depend on Options from `nightly-prod-lock-vs-tip`, `nightly-vendor-test-execution` and `prod-manifest-dev-tooling`; server installs depend on the `--no-dev` prod branch and on the lock staying fresh; every future bagart release depends on the tag-hijack refresh obligation; all CI package resolution depends on proxy-repo visibility and on the uniform `main`-as-default topology.
- **Follow-ups:** refresh `composer.prod.lock` immediately after any future `cmd/release/lib` tag (plus a still-missing tip-freshness control in `cmd/deps/check`); revisit weekly tip-of-tree runs (option C of `nightly-prod-lock-vs-tip`) after the Q7 step-5 checkpoint is stable; complete the proxy-repo secret audit if not already done before/with visibility flip; optional cleanup of the duplicate `origin/master` antispam ref; composer-SBOM stays deferred unless a formal attestation request arrives; `lock-fresh:prod` semantics remain "lock↔manifest consistency", not tip freshness, so freshness is a process obligation rather than a control.
