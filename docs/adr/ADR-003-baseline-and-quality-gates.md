# ADR-003: Baseline and Quality Gates

> Status: accepted
> Date: 2026-10-08

## Context

Seven grilling questions reached resolution inside a single wave and all describe one decision surface: how the platform's baseline tooling and quality gates are wired, enforced, and kept trustworthy while the baseline package is under its Phase-0 freeze. They were forced by concrete pressures rather than theory. The baseline package (`telegram-platform-devops-baseline`) froze `cmd/lib`, `controls/` and `hooks/` until consumer rollout completes, so every proposed gate edit had to weigh a package-first approval path against a host-side shortcut. The package's `controls/` zone was meanwhile found to contain four silent no-op shims (false-green via the `realpath($argv[0])` guard) with `sec-invariants` direct at 9/12, and 26 (actually ~35) host shims still await Phase-7 retirement — so the reliability of that venue itself was in question when a new module-namespace validator wanted to register as a blocking control.

Quality floors had the same problem in a different shape: both the coverage floor (`BASELINE_COVERAGE_MIN: 55`) and all 12 per-library mutation floors were decorative — never validated, never blocking, with `continue-on-error` set and, in mutation's case, a dead gate lookup that made even real floors inert. Promoting them to blocking gates therefore meant first measuring honest baselines and then flipping both jobs together without creating a permanent wrong-reason red. A CI-exact prod simulation additionally broke the Pest arch suite (`toImplement` on vendor-path classes) and blocked the 3-green-runs promotion path, while generated skills churn from `boost:install` / `cmd/sync-skills` left ~100 host files dirty with no commit policy. The remaining question was a bookkeeping gate: where a new module check may legitimately block, given a frozen package, a compromised controls zone, and a red module workflow awaiting repair.

## Decision

### Baseline-check gate registration policy (source question: `baseline-check-gate-registration-policy`, resolved 2026-10-07)

**Option 2.** The `<module>:` namespace validator blocks only as a step in `.github/workflows/module-validation.yml`, and only after W-D1 repairs that workflow (grandfathered per Q7 so it starts green); it is **never** registered in `bin/baseline-check` absent an explicit owner reopening of K25 (the nightly-only venue precedent from the mutation gate), K29 (four false-green shims in that controls zone, `sec-invariants` direct 9/12) and K28 (Phase-0 package-first approval). Q7's wiring sub-choice (a) is therefore closed, and Q2's §5 wiring phrasing becomes "report-only everywhere else; blocking in `module-validation.yml` once W-D1 repairs it". Rejected: option 1 (register in `bin/baseline-check`) — four resolved constraints against it (K25, K24, K29, K28) and it would buy local enforcement for a rule that does not exist yet; option 3 (both, sequenced) — it is option 2 plus a promise, re-opens the venue problem for no present gain, and survives only as a future fresh decision after a green period, not as a commitment. Binding follow-ups: the W-D1 repair still needs its own task file, and since the repo has no required checks (repair-spec RK4, re-verified 2026-10-07), configuring a ruleset/required check is the step that would turn this red job into a merge gate — record it in W-D1's DoD if gating is wanted.

### Baseline freeze — commit the 5 dirty package files (source question: `baseline-freeze-f3`, resolved 2026-10-01)

**Option A — commit as policy fixes**, executor: user (2026-10-01). One proposed commit: `chore(baseline): artifact-scan, github-policy, semgrep rules + selftest fixes` (+51/−20 across `controls/artifact-scan.sh`, `controls/github-policy.php`, `defaults/semgrep-rules.yml`, `selftest/{cycle,engine}-smoke.sh`), all inside the Phase-0 frozen zone. Rejected: option B (revert in package, keep nothing dirty) — the diffs are rollout fixes (selftest smoke + policy controls), not baseline refactors, and the freeze targets refactors while the host gate currently depends on these files being green.

### Baseline Phase 7 — shim retirement (source question: `baseline-phase7-shim-retirement`, resolved 2026-09-29)

**Option B — defer full shim retirement** (~35 caller/test/doc files plus a frozen-zone package fix for zero user-visible gain; rollout not evidenced). Rejected: option A (retire now) — it would touch the frozen baseline surface before consumer rollout is confirmed, spans 14 execution callers + 15 test files + MANIFEST regen + AGENTS/CLAUDE/GEMINI mirrors, and delivers no user gain. Binding recorded follow-ups: (i) package-side issue for the 4 silent-no-op shims (`realpath($argv[0])` guard in `controls/{baseline-config,mutation-gate,sec-invariants,telemetry}.php`) — package first per Phase-0 freeze; (ii) broken `core.hooksPath` (points to nonexistent `telegram-devops-baseline/hooks`) — one `bash cmd/dev/setup`; (iii) optional micro-action: delete the 4 dead shims (`changed-surface.php`, `cycle-smoke.sh`, `engine-smoke.sh`, `semgrep-scan.sh`) + manifest regen.

### Coverage gate floor (source question: `coverage-min-threshold`, resolved 2026-10-03)

**Option A — `BASELINE_COVERAGE_MIN: 30`**, decided 2026-10-03. The floor was set to **30**, just below the measured baseline (31.8% pcov in CI run 37109056833 / 32.1% xdebug locally — drivers agree within 0.3pp), and both jobs became blocking in the same flip after 3 consecutive green all-blocking nightly runs (37114626742, 37115186051, 37115739626) on 2026-10-03; `continue-on-error` was dropped on coverage and mutation together, pin `c13903f`. Measurement command of record: `vendor/bin/pest --coverage --min=${BASELINE_COVERAGE_MIN}` in `misc/BAGArt/telegram-platform-workflows/.github/workflows/nightly.yml` (floor at line 121, command at line 160). Rejected: option B (keep 55 + `continue-on-error`) — leaves the floor decorative and violates step 2c's both-jobs flip; option C (raise coverage to 55) — ~23pp of new tests is outside Wave C scope; option D (floor 32) — zero margin for driver/runner variance. Binding obligation: the floor is raised only as coverage actually improves, and each raise = workflows commit + host pin bump.

### Mutation floor enforcement (source question: `mutation-floor-enforcement`, resolved 2026-09-29)

**Option C (amended by research)** — enforce async-kernel only; the other 11 libraries stay report-only with `msi_floor: 0`. Prerequisites in strict order: (1) fix the dead-gate bug — `cmd/dev/mutate:37` calls engine `controls/mutation-gate.php` with explicit `--baseline="$REPO_ROOT/tools/baseline/mutation-baseline.json"`, and strengthen `MutationGateTest` to assert a non-empty floor; (2) measure async-kernel once locally with `--parallel`, set `msi_floor = floor(score − 3.0)` for `bagart/async-kernel` only, then `manifest.php --generate`; (3) fix nightly (missing `SettingsScreenContribution` stub at shared `nightly.yml:38/132/187`; add `--parallel` to `cmd/dev/mutate:42`); (4) after 3 green nightly mutation runs → drop `continue-on-error` on shared `nightly.yml:171` → bump host pin `.github/workflows/nightly.yml:14` → then evaluate coverage → update `docs/STATUS.md:38`. Binding venue rule: **not registered in `bin/baseline-check` (nightly-only)**. Rejected: option A (full enforcement of all 12 libraries) — ruled out by measured ~200+ CPU-hours per run; option B (keep report-only, document as accepted) — superseded by the amended plan. `covered_code_msi_floor` has no consumer and must not be set. Decided 2026-09-29.

### Skills sync churn (source question: `skills-sync-churn`, resolved 2026-10-01)

**Option A — wholesale chore commit**, executor: user (2026-10-01): run `bash cmd/sync-skills --check`, then one `chore: sync agent skills` commit covering the ~100 generated skills files under `.agents/`, `.claude/`, `.cursor/`, `.github/`, `.junie/`. Rejected: option B (`git restore` everything skills-related) and option C (leave dirty) — the churn is generated by sanctioned tooling (`php artisan boost:install` + `bash cmd/sync-skills`), and committing keeps future deltas reviewable.

### Pest arch `toImplement` for vendor-path classes (source question: `pest-arch-toimplement-vendor`, resolved 2026-10-03)

**Option A**, executor: user (2026-10-03) — rewrite the arch `toImplement` expectations on platform classes to Reflection-based checks (`class_implements()` / `ReflectionClass::implementsInterface()`) in the affected nested repos (`telegram-bot-lib`, `php-async-kernel-client-redis`, `telegram-platform-management`: 6 assertions in 7 files), push them, refresh the prod lock pins via `cmd/deps/update --mode=prod`, and record the standing rule: **"no pest-arch `toImplement` expectations on platform classes (vendor-mode CI) — use Reflection"**. Rejected: option B (skip the 6 tests in vendor-mode) — skips read green and lose the contract checks, i.e. pure signal loss while still needing the recorded rule; option C (wait for upstream fix) — unbounded external timeline while nightly must go green now (3-green-runs blocker), and the installed `pest-plugin-arch v4.0.2` is the newest 4.x release with no drop-in fix. `tools/baseline/test-quarantine.json` was explicitly not an option: the quarantine control is a separate check and `tests/Pest.php` does not read the list. Decision recorded 2026-10-03, execution started same day.

## Consequences

Contracts and surfaces touched: `bin/baseline-check` registration policy (`engine_register` venue — stays closed to the module validator and to the mutation gate, nightly-only for mutation); the shared `telegram-platform-workflows` nightly (coverage + mutation `continue-on-error` now dropped together, floor 30, host pin bumped to `c13903f`); `tools/baseline/mutation-baseline.json` floors (async-kernel non-zero, `floor(score − 3.0)`, manifest regen) and `cmd/dev/mutate`; the frozen baseline package `controls/` / `selftest/` / `defaults/` (5 policy-fix files committed); the 26→35 host shim surface under `tools/baseline/` (manifest-tracked) and `core.hooksPath`; generated skills trees under `.agents/`/`.claude/`/`.cursor/`/`.github/`/`.junie/`; arch test code in 3 nested repos plus their `composer.prod.lock` pins.

Dependents: Q7 (`namespace-validator-strictness`) wiring and Q2 §5 phrasing; W-D1 / W-Q2 sequencing; `docs/STATUS.md` and `dev-ai.md` gate-promotion wording ("coverage blocking at floor 30"); the 3-green-runs promotion path that the nightly stub fix unblocks; future test-writing guidelines (no arch `toImplement` on platform classes in vendor-mode).

Follow-ups that remain binding: W-D1's own task file and the `module-validation.yml` repair; ruleset/required-check configuration if merge gating is wanted (recorded in W-D1's DoD); package-side issue for the 4 silent-no-op shims (package first per Phase-0 freeze); one `bash cmd/dev/setup` to repair `core.hooksPath`; optional deletion of the 4 dead shims + manifest regen; coverage-floor raises only as coverage improves (each raise = workflows commit + host pin bump); future local controls require a fresh K28/K29-cleared approval.
