## 1. Purpose

This document defines the contracts specific to the Telegram platform that the
generic documents (01–09) do not cover. It is the single home for:

- bot credential handling and token-leak controls (F-19);
- webhook endpoint security (IP allowlist + secret-token validation);
- the `telegram` tooling/CI profile;
- Telegram-specific invariants (TG-01…TG-08).

Platform baseline: PHP 8.5, Laravel app, PostgreSQL + Redis (no RabbitMQ), Inertia/React admin.

## 2. Platform Components & Library Map

Libraries live in `misc/BAGArt/` and are wired via Composer `path`
repositories; `vendor/bagart/` contains symlinks into `misc/BAGArt/`, so local
changes are immediately visible without re-publishing.

| Library | Role | Framework coupling | Key contracts / artifacts |
|---|---|---|---|
| `telegram-bot-lib` | Pure Telegram Bot API library | None (plain PHP) | Auto-generated API DTOs under `src/TgApi/`; outbound queue/DLQ/pipeline types |
| `telegram-bot-basic-lib` | Webhook handlers, middleware, command layer | Works with plain PHP and Laravel | Update handlers, middleware chain |
| `telegram-bot-management-lib` | Multi-bot management | Laravel (Eloquent models) | `TgBot` / `TgBotOwner` / `TgBotModule`, DB token resolution, `TgWebhookController`, IP-validator, secret-validator, bot-id-resolver middlewares |
| `php-async-kernel-lib` | Fiber-based cooperative scheduler | None (plain PHP) | `AsyncKernel`, daemons, tickables, graceful shutdown |

Rules:

- Strict contracts between libraries: cross-boundary calls go through declared
  interfaces only — no duck-typing (`method_exists`, `instanceof` probing).
- Generated DTOs under `src/TgApi/` are regenerated by script and never
  hand-edited (see TG-06).

## 3. Bot Credentials & Token Handling

This section is the F-19 core. Bot tokens are secrets of the same class as
database credentials (see 03-security-and-supply-chain.md for generic secret
policy; this section is authoritative for Telegram tokens).

Storage:

- Tokens are stored in the database (`tg_bots` table), NEVER in `.env`.
- Access to tokens is restricted to the runtime (token resolution at request /
  delivery time) and admin functionality. No other code path may read them.

Exclusion surfaces — a token must never appear in:

- logs (application logs, access logs, daemon output);
- error messages or exception texts (including wrapped/chained messages);
- telemetry labels, metric tags, trace attributes, correlation metadata.

Secret scanning:

- CI runs a repo-wide scanner detecting the Telegram token format
  `[0-9]{5,}:[A-Za-z0-9_-]{30,}`.
- The scan covers all files including DB seeders and fixtures; a match fails
  the build.

Rotation procedure (per bot):

1. Revoke the token via BotFather.
2. Update the token in the `tg_bots` table.
3. Restart workers so runtime caches pick up the new token.

Webhook secrets are generated per bot and compared using constant-time
comparison only.

## 4. Webhook Security

Two endpoints exist, both behind Telegram IP CIDR allowlist and
secret-token validation middleware:

| Endpoint | Bot resolution |
|---|---|
| `POST /tg/` | Bot resolved from the secret token header |
| `POST /tg/webhook/{bot_id}` | Token resolved from the database by `{bot_id}` |

Controls:

- IP allowlist restricted to official Telegram CIDR ranges; requests from
  other sources are rejected before any processing.
- Secret-token validation on every request; comparison is constant-time.
- No unauthenticated diagnostics on webhook routes (no debug dumps, no health
  probes that echo update contents).
- Updates are validated and normalized before processing; malformed payloads
  are rejected without leaking internals in responses.

## 5. Outbound Delivery Reliability

Outbound delivery is Redis-backed (no RabbitMQ):

- Queue channel: `tg-outbound`.
- Per-bot dead-letter queue: `tg-dlq:{botId}`.
- Stats counters: `tg_outbound:stats`.

Model rules:

- Only readonly state DTOs are stored in Redis — no connections, closures, or
  objects with behavior.
- Retries are bounded (retry budget); exhausted tasks move to the DLQ.
- A circuit breaker protects against cascading failures toward the Telegram
  API.
- Rate-limit handling (429 / `retry_after`) is centralized in one place — see
  06-runtime-operations.md §24–§25.
- Graceful shutdown drains in-flight work before exit.
- Performance optimizations must never disable TLS verification or limits —
  see 03-security-and-supply-chain.md §61.

## 6. The `telegram` Profile

The `telegram` profile enables the following in tooling/CI when the platform
surface is in scope:

- transport tests against the Telegram API client layer (TLS, timeouts,
  429/5xx handling, malformed responses);
- contract tests across the four libraries;
- token-leak scans (Section 3 pattern, repo-wide);
- 429/throttling test fixtures;
- async-runtime tests for scheduler/daemon behavior.

The profile composes with `laravel`, `async-runtime`, and `docker`: enabling
`telegram` implies the relevant parts of those profiles rather than
duplicating them.

## 7. Testing & Compatibility

Overall strategy, coverage targets, and CI placement are defined in
04-qa-and-testing.md. This section lists the Telegram-specific surfaces only:

- Transport: TLS verification, connect/read timeouts, 429 with `retry_after`,
  5xx responses, malformed payloads.
- Contract tests across the four libraries (explicit interfaces, no
  duck-typing paths).
- Compatibility matrix: PHP versions × sync/async transport × Redis on/off.

## 8. Observability

Metrics collection, dashboards, and alerting rules are defined in
06-runtime-operations.md and 09-observability-and-performance.md.
Telegram-specific rules:

- Metrics: outbound queue depth, DLQ size per bot, circuit-breaker state,
  429/retry counts, delivery latency.
- Log redaction: no tokens, no private message content — ever (TG-07).
- Correlation IDs propagate through the full path: update → processor →
  queue → worker → API call.

## 9. Acceptance Criteria

- [ ] Bot tokens exist only in the `tg_bots` table; never in `.env`, logs,
      error messages, or telemetry labels (Section 3).
- [ ] Secret scanner covers the Telegram token pattern repo-wide, including
      seeders/fixtures, and fails CI on match (Section 3).
- [ ] Rotation procedure documented and executable: revoke → update DB →
      restart workers (Section 3).
- [ ] Both webhook endpoints specified with IP CIDR allowlist, constant-time
      secret validation, and no unauthenticated diagnostics (Section 4).
- [ ] Outbound model uses `tg-outbound`, `tg-dlq:{botId}`,
      `tg_outbound:stats`; retries bounded; rate limiting centralized
      (Section 5).
- [ ] `telegram` profile defined and composes with `laravel`,
      `async-runtime`, `docker` (Section 6).
- [ ] Compatibility matrix (PHP × transport × Redis) listed (Section 7).
- [ ] Observability rules include redaction and end-to-end correlation IDs
      (Section 8).
- [ ] Invariants TG-01…TG-08 present and sequential (Section 10).

## 10. Architectural Invariants

### TG-01 — Tokens never leave the DB/runtime boundary

Bot tokens are read from `tg_bots` at runtime/admin boundaries only and are
never copied into config files, environment variables, caches outside the
runtime, or any persistent store.

### TG-02 — Webhook surface is always IP+secret validated

Every webhook endpoint (`POST /tg/`, `POST /tg/webhook/{bot_id}`) enforces the
Telegram IP CIDR allowlist and secret-token validation. A new route may not be
added to the webhook surface without both controls.

### TG-03 — One scheduler/one runtime per process

Exactly one `AsyncKernel` scheduler/runtime instance exists per process —
see 06-runtime-operations.md §6.

### TG-04 — Outbound retries are bounded and centrally rate-limited

Retry budgets are finite; exhausted work goes to the per-bot DLQ. All 429 /
`retry_after` handling flows through the single central rate limiter
(06-runtime-operations.md §24–§25); ad-hoc sleeps or per-call retry loops are
forbidden.

### TG-05 — Libraries communicate via explicit contracts only

Cross-library calls between the four BAGArt libraries go through declared
interfaces. No `method_exists`, no `instanceof` duck-typing across library
boundaries.

### TG-06 — Generated API DTOs are never hand-edited

Files under `src/TgApi/` are produced by the generator script. Fixes go into
the generator or mapping configuration, then regenerate.

### TG-07 — Logs/telemetry never contain credentials or private message content

No token, webhook secret, or user message content may appear in logs, error
messages, metrics labels, or trace attributes.

### TG-08 — Restore/test environments cannot send real Telegram messages

Restore, staging, and test environments must be unable to deliver real
messages to the Telegram API — see 07-resilience-and-disaster-recovery.md §37.
